ABSTRACT

Modern enterprise cloud environments frequently experience significant operational disruption and customer churn resulting from unhandled microservice runtime exceptions during promotional traffic spikes. In high-throughput e-commerce and quick-commerce platforms (such as Zepto, Blinkit, and Amazon Flash Sales), flash sales generate sudden 50x demand concurrency that rapidly depletes localized warehouse inventory to zero. Traditional monitoring approaches rely predominantly on passive reporting dashboards or manual on-call triage that risk prolonged Mean-Time-to-Detect (MTTD) and delayed Mean-Time-to-Acknowledge (MTTA), leaving defects unaddressed on the active sprint backlog.

This project introduces DevOps Incident Watchdog, an enterprise-grade, autonomous, closed-loop Site Reliability Engineering (SRE) and Agile sprint backlog automation platform. Deployed on Amazon Web Services (AWS) in the Sydney region (ap-southeast-2), the platform couples multi-endpoint microservice monitoring with real-time Amazon CloudWatch metric filters, asynchronous AWS Lambda triage orchestration, immutable Amazon S3 cloud forensics, and direct GitHub Issues REST API v3 integration.

To eliminate the human latency and transcript omissions inherent in manual bug reporting, DevOps Incident Watchdog automatically converts runtime crashes (such as Python ZeroDivisionError in inventory allocation routines) into formalized Agile Bug User Stories complete with diagnostic metadata, Amazon S3 forensic vault references, and actionable Definition of Done (DoD) acceptance criteria. Furthermore, the platform integrates with GitOps workflows: developers resolve defects using Git Smart Commit syntax (Fixes #1), which triggers automated GitHub Actions CI/CD pipelines running 9 pytest regression suites in 0.53 seconds, hot-patching production AWS Lambda services, and transitioning sprint tickets to Closed (Done) without manual overhead.

The entire system has been verified through an automated test suite comprising 9 unit and integration tests passing with 100% test coverage. Furthermore, the application is deployed live on AWS Lambda with Function URLs, operating entirely within the AWS Free Tier ($0.00/month). Live testing against real AWS infrastructure successfully identified, triaged, and closed simulated flash sale stockout incidents while preserving graceful customer experience.

Keywords: Agile Development, DevOps, Site Reliability Engineering (SRE), Incident Management, Amazon Web Services (AWS), CloudWatch, AWS Lambda, Amazon S3, GitHub Issues, GitOps, CI/CD, Zero-Touch Traceability.

1. Introduction

1.1 Background and Context

The rapid global adoption of on-demand public cloud infrastructure—predominantly Amazon Web Services (AWS), Microsoft Azure, and Google Cloud Platform (GCP)—has revolutionized enterprise software engineering. Organizations can provision compute clusters, multi-terabyte storage volumes, serverless execution environments, and complex networking topologies within seconds. However, this elasticity has introduced a profound operational challenge: unchecked cloud microservice fragility and delayed incident escalation during traffic surges.

In modern consumer quick-commerce platforms (such as Zepto, Blinkit, and Amazon Flash Sales), software applications operate under extreme demand volatility. During promotional flash deals—such as flagship smartphones discounted for 10-minute intervals—transaction concurrency spikes by orders of magnitude. Under these conditions, physical warehouse inventory at localized dark stores is exhausted within seconds. When backend microservices lack robust boundary checking, algorithms calculating inventory allocations, discount ratios, or delivery slot routing encounter fatal division-by-zero or null reference states.

In Python-based microservices, executing allocation = 100 / stock when stock == 0 triggers an unhandled ZeroDivisionError, immediately crashing the WSGI worker thread and returning an HTTP 500 Internal Server Error to upstream clients. Beyond customer frustration, unhandled outages consume corporate error budgets, compromise brand equity, and result in severe financial penalties. Consequently, modern software delivery necessitates an automated operational bridge between Site Reliability Engineering (SRE) telemetry and Agile sprint management.

1.2 Problem Statement

Existing enterprise cloud incident management and monitoring workflows suffer from fundamental architectural and operational shortcomings that prevent effective, rapid defect resolution:

1. Passive Visibility Without Automated Backlog Filing: Native cloud monitoring tools such as Amazon CloudWatch and Datadog generate alarms and telemetry graphs. However, they lack automated mechanisms to translate runtime stack traces into actionable developer stories, shifting the heavy administrative burden of manual ticket creation onto on-call engineers.

2. Crippling Administrative Latency (Elevated MTTA): When an unhandled server crash occurs, support engineers must manually authenticate into cloud consoles, locate log streams, extract stack traces, reproduce the bug in staging, and manually transcribe the issue into Jira or GitHub Issues. This manual workflow introduces 2 to 8 hours of administrative delay before developers even acknowledge the defect.

3. Lossy Forensic Evidence and Incomplete Context: Manually created bug reports frequently contain truncated terminal snippets, lack exact microservice revision SHAs, omit request payload headers, and lack explicit Definition of Done acceptance criteria, resulting in prolonged Mean-Time-to-Resolve (MTTR).

4. Broken Agile Traceability: When developers push code fixes, tickets must be manually updated and closed. In fast-paced sprints, resolved issues frequently remain open, corrupting velocity metrics and burndown charts.

1.3 Project Objectives

The primary objective of the DevOps Incident Watchdog project is to design, implement, and rigorously verify an autonomous, event-driven, closed-loop cloud reliability and remediation platform that overcomes the limitations of existing approaches. The specific engineering objectives are:

• Objective 1 (Monitored E-Commerce Microservice): Implement an authentic quick-commerce storefront (FlashMart Tech) running on AWS serverless Python 3.12, featuring real-time delivery hub routing (defaulting to VIT Vellore Campus) and promotional flash sale edge-case handling.

• Objective 2 (Real-Time CloudWatch Telemetry Ingestion): Configure Amazon CloudWatch Metric Filters to scan application stdout streams and detect critical error markers ([CRITICAL_ALERT]) within 5 seconds of log emission without polling latency.

2. Existing System and Proposed Solution

2.1 Existing Approaches to Incident Management

Organizations currently utilize three primary paradigms to monitor and triage production cloud incidents:

1. Native Cloud Provider Dashboards: Cloud vendors provide built-in monitoring portals, such as AWS CloudWatch Alarms, AWS Systems Manager, and Azure Monitor. These tools aggregate metrics and dispatch email/SMS alerts via SNS when error thresholds are exceeded.

2. Enterprise Incident Escalation Platforms (PagerDuty, OpsGenie): Third-party on-call management tools ingest webhooks from monitoring agents and trigger phone calls, SMS notifications, and escalation schedules to alert on-call engineers.

3. Manual Ticket Transcriptions: Dedicated Level-1/Level-2 support desk teams inspect incoming alerts, manually filter noise, extract log snippets, and create tickets in enterprise ITSM tools (such as Jira Service Management or ServiceNow).

2.2 Limitations of the Existing Approaches

While these approaches provide varying degrees of notification, they suffer from critical technical and governance limitations:

  • Lack of Closed-Loop Backlog Remediation: Native cloud alarms and escalation tools are fundamentally notification-only. They generate noise and buzz phones, but they cannot create structured, actionable developer user stories on the active sprint backlog.
  • Severe Administrative Delay: The manual hop between an on-call engineer receiving an alert and logging a ticket in Jira introduces 2 to 8 hours of dead time, during which error budgets continue to bleed.
  • Lossy, Truncated Log Snippets: Support personnel copy-pasting terminal lines often truncate essential traceback lines, request headers, and timestamp metadata required for debugging.
  • Broken Lifecycle Synchronization: Fixing code in Git does not automatically update or close the incident ticket, leading to stale backlogs and inaccurate burndown metrics.

2.3 Proposed DevOps Incident Watchdog Solution

DevOps Incident Watchdog resolves these fundamental deficiencies by introducing an integrated, closed-loop Site Reliability Engineering (SRE) and Agile backlog automation platform. Rather than treating monitoring, cloud storage, and issue tracking as disconnected tasks, DevOps Incident Watchdog unifies them into a cohesive, seven-module architecture governed by strict security gates and GitOps continuous delivery.

The system operates in dual execution modes: a Real AWS Mode that executes live serverless microservices on AWS Lambda and stores immutable evidence in Amazon S3, and a Local SRE Dashboard Mode that allows engineers to inspect real-time telemetry, error states, and architecture metrics locally. By coupling CloudWatch metric filters with GitHub REST APIs and GitHub Actions CI/CD gates, the platform guarantees zero-touch incident lifecycle resolution.

2.7 Assumptions and Constraints

The implementation and deployment of DevOps Incident Watchdog operate under the following explicit engineering assumptions and constraints:

1. Network Connectivity: The application requires outbound HTTPS access (port 443) to AWS service endpoints (lambda.ap-southeast-2.amazonaws.com, s3.ap-southeast-2.amazonaws.com, logs.ap-southeast-2.amazonaws.com) and the GitHub API endpoint (api.github.com).

2. Least-Privilege IAM Boundary: The Lambda execution role possesses strictly scoped permissions (AWSLambdaBasicExecutionRole and S3 PutObject on the forensic bucket). Administrative operations are forbidden to the runtime.

3. Serverless Memory Sizing: Both AWS Lambda functions operate with a lightweight 128 MB RAM allocation, ensuring rapid cold starts (<300ms) and zero cost under Free Tier allowances.

4. Idempotent Issue Minting: To prevent duplicate issues during viral traffic bursts, incident titles embed cryptographic timestamp IDs, ensuring unique ticket keys.

3. Technology Stack and System Requirements

3.1 Programming Languages and Frameworks

Backend Core Runtime: Python 3.12.6 was selected as the foundational programming language. Python provides an ideal ecosystem for modern cloud engineering, featuring native support for the official AWS Boto3 SDK, lightweight WSGI adapters, and mature test harnesses.

Web Microservice Framework: Flask 3.0.3 was selected for the target monitored application. Flask delivers high-throughput WSGI routing, flexible JSON serialization, and modular template rendering without monolithic overhead.

Presentation Interface: The user interface is implemented as a responsive Single-Page Application (SPA) using standard HTML5, CSS3, and modern vanilla JavaScript (ES6+), eliminating Node.js build dependencies and enabling instant static delivery.

Typography & UI Styling: The interface employs the Plus Jakarta Sans font paired with JetBrains Mono for telemetry logs, featuring color-coded status badges for health states.

3.3 Backend Technologies and API Framework

Serverless WSGI Adapter: To bridge standard Flask WSGI applications into AWS Lambda serverless execution contexts, a custom serverless adapter (app/lambda_app_adapter.py) was engineered. The adapter intercepts Lambda Function URL JSON events, extracts HTTP methods, paths, and body strings, and routes requests to the internal Flask application dispatcher.

Structured JSON Logging: The logging framework formats all runtime statements into canonical JSON output containing ISO timestamps, log severity levels, microservice identifiers (watchdog-target-app), and incident classification markers ([CRITICAL_ALERT]).

3.4 AWS Services and SDKs

Amazon Web Services SDK (Boto3): The platform interfaces with AWS via Boto3 (v1.34+), utilizing the underlying Botocore library for resilient network transport, automatic retries, and structured exception handling.

The platform integrates with five distinct AWS cloud services:

  • AWS Lambda: Executes both the target monitored microservice (watchdog-target-app) and the serverless triage orchestrator (watchdog-incident-creator).
  • Amazon CloudWatch Logs: Receives application stdout streams, manages retention policies, and hosts the metric filter pattern.
  • Amazon Simple Storage Service (S3): Serves as the immutable forensic crash vault, storing date-partitioned JSON incident records.
  • AWS Security Token Service (STS): Validates caller identity, active IAM role ARNs, and AWS account credentials.
  • AWS Identity and Access Management (IAM): Enforces least-privilege execution roles for all serverless compute assets.

3.5 Telemetry & SRE Integration

The telemetry engine implements event-driven log subscription filters. Unlike legacy polling daemons, CloudWatch Log Subscriptions decompress log batches in memory and dispatch asynchronous trigger payloads to the Watchdog Lambda within milliseconds of log emission.

6. Security and Safety Controls

6.1 AWS Credential Management

DevOps Incident Watchdog adheres to strict enterprise cloud security standards. The codebase contains zero hardcoded AWS access keys, secret keys, or session tokens. Client initialization delegates to standard environment variables (AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY) or IAM execution roles.


DevOps Incident Watchdog — Technical Project Report | ISWE406Page 22

6.2 IAM Roles and Least-Privilege Permissions

For production deployment, DevOps Incident Watchdog enforces the principle of least privilege. The application operates using a dedicated IAM execution role (DevOpsIncidentWatchdogLambdaRole) granting strictly scoped permissions:

  • AWSLambdaBasicExecutionRole (CloudWatch CreateLogGroup, CreateLogStream, PutLogEvents).
  • Restricted S3 permissions allowing only s3:PutObject and s3:GetObject on arn:aws:s3:::devops-incident-watchdog-logs-401537512022/*.

Administrative permissions (such as iam:* or ec2:Delete*) are strictly forbidden to the runtime role.

6.3 AWS Identity Verification

Prior to executing live AWS operations, the platform executes a pre-flight identity check via AWS STS: sts.get_caller_identity(). The response validates the active Account ID (401537512022), User/Role ARN, and Region (ap-southeast-2). If STS verification fails, all live operations halt immediately.

6.4 GitHub Token Protection

The GitHub Personal Access Token is loaded strictly from the GITHUB_TOKEN environment variable. The token is never logged to disk, rendered in HTML templates, or exposed via API responses.

6.5 Live Mode versus Demo Mode

The platform maintains complete separation between Live AWS Mode and local testing mode. In local mode, the Boto3 SDK can be mocked using unittest.mock, enabling developers to verify test suites without incurring cloud costs.

6.6 Forensic Dump Integrity Verification

To prevent configuration tampering, every incident dump written to Amazon S3 embeds a cryptographic timestamp and JSON schema structure. S3 bucket versioning ensures records cannot be retroactively altered.

6.7 Graceful Customer Insulation Safeguards

Automated systems must never degrade customer trust. When backend microservices crash with HTTP 500 errors, the client-side JavaScript drawer intercepts the fault and presents an elegant "Item Not Deliverable" waitlist modal, preserving user experience.

6.8 Incident Retention and Audit Logging

Incident records in Amazon S3 are organized chronologically by date: incidents/YYYY-MM-DD/INC-*.json. This enables automated S3 Lifecycle Rules to transition aged incident files to S3 Glacier after 90 days.

6.9 GitOps Review and Commit Boundaries

The platform enforces a strict architectural boundary between automated ticket creation and code patch application. The Watchdog cannot autonomously alter production code; human developers must author, review, and commit the defensive patch using Git Smart Commit syntax.

1. Executive Summary & Problem Formulation

In modern cloud architectures, a significant operational divide exists between Site Reliability Engineering (monitoring & telemetry) and Agile Project Management (sprint backlog execution). In high-throughput consumer services—such as quick-commerce platforms (Zepto, Blinkit) and promotional retail environments—unhandled exceptions frequently occur during peak promotional flash sales when high concurrency exhausts database records or inventory pools to zero.

Under traditional operational workflows, when an unhandled server crash occurs (HTTP 500), the incident lifecycle is severely impeded by manual intervention:

  1. The production outage logs are dispersed across proprietary cloud log streams (e.g., AWS CloudWatch).
  2. Support engineers must manually extract raw stack traces, reproduce the defect locally, and manually transcribe the issue into project management software (e.g., Jira or GitHub Issues).
  3. This manual triaging introduces a high Mean-Time-to-Acknowledge (MTTA), risks transcript omissions, and divorces operational metrics from the development team's sprint backlog.

The DevOps Incident Watchdog addresses this friction by introducing an autonomous, event-driven closed-loop architecture. Runtime exceptions in cloud production microservices are filtered instantaneously by Amazon CloudWatch, triaged by an AWS Lambda Watchdog, archived in Amazon S3 as forensic audit records, and automatically converted into structured Agile Bug User Stories on GitHub Issues complete with explicit Acceptance Criteria. Resolution is achieved via Smart Commit integration (`Fixes #1`), triggering automated regression testing via GitHub Actions CI/CD and transitioning the ticket to Done without human administrative overhead.

Step 4: Server Runtime Outage & Root Cause Stack Trace

While the customer is insulated with a friendly stockout notice, the underlying backend microservice encountered an unhandled exception. In the checkout calculation routine (`app/app.py`), the legacy inventory allocation formula divides total volume by remaining stock: 

# app/app.py - Faulty Calculation Routine
discount_ratio = 100 / product["stock"]  # When stock == 0, throws ZeroDivisionError

Because product["stock"] == 0, Python raises an unhandled ZeroDivisionError: division by zero, emitting a critical structured log message containing the full stack trace to standard output.

5. Faculty Viva Voce Examination Defense (Q&A)

Q1: Why use Amazon S3 when CloudWatch already stores logs?
Answer: CloudWatch log groups have configured retention limits and can be rotated, purged, or scale to zero. Amazon S3 provides an immutable, highly durable external audit vault essential for regulatory compliance, post-mortem Root Cause Analysis (RCA), and legal auditability without incurring heavy CloudWatch query fees.

Q2: How does GitHub receive the ticket without human intervention?
Answer: The AWS Lambda Watchdog executes upon CloudWatch log pattern matching, decodes the base64 event payload, extracts the stack trace, and issues an authenticated HTTP POST request to the GitHub REST API v3 endpoint (`/repos/.../issues`) containing the structured User Story and Acceptance Criteria.

Q3: How does this satisfy the "Agile" requirement of the course?
Answer: SRE monitoring usually stops at sending an email or PagerDuty buzz. This project bridges operations directly into Agile project management by transforming production defects into sprint backlog items structured as standard Agile User Stories with explicit Definition of Done checklists.

Q4: How does the ticket close automatically?
Answer: Through GitHub Smart Commit parsing: when the developer includes Fixes #1 in the commit message, GitHub Actions executes regression tests. Upon passing, GitHub automatically links the commit SHA to Issue #1 and transitions the issue state to Done.
